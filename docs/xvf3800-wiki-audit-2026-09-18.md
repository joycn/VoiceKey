# XVF3800 + XIAO 官方资料核对

> 后续修复：播放资格检查、维护诊断镜像、范围与验收契约已完成软件修复和构建；本报告下文保留审查时发现。实机烧录与验收仍待完成，见[修复记录](device-records/2026-09-18-review-repair.md)。

日期：2026-09-18。范围：Seeed Wiki 的 XVF3800/XIAO 相关页面及其引用的部分实现，对照当前工作区；这是资料与代码审查，不是新增实机验收。本轮未修改固件、未再次烧录。

## 结论

48 kHz、XVF3800 为 I²S 主机、XIAO 为从机的方向有官方示例支持；已采用的音频/I²C 引脚没有发现与这些示例冲突。不能因此认定完整 VoiceKey 固件已可用。主要缺口是板上 XMOS 配置尚未确认、XIAO 应用没有成功枚举，以及模拟播放/AEC 链路尚未实测。

当前唯一实机结论见 [首次烧录记录](device-records/2026-09-18-first-flash.md)：XIAO 的四个镜像写入校验通过；重启后未观察到 VoiceKey USB/audio/HID。XMOS 本轮没有被烧录或读出版本。编译、写入校验、应用运行、音频工作是四个不同检查点。

## 可以保留的配置

| 项目 | 核对结果 |
| --- | --- |
| I²S 时钟 | Home Assistant 与 WebSocket 示例支持 XMOS 提供时钟、XIAO 从模式、48 kHz/32-bit/stereo；基础 Arduino 16 kHz 主模式属于另一套配置，不能混用。 |
| 引脚 | BCLK 8、WS 7、XIAO RX 43、TX 44；I²C SDA 5、SCL 6，与相关示例一致。 |
| XMOS 目标镜像 | DOA/VAD 页面列出 `application_xvf3800_i2s_master_v1.0.8_48k.bin`。项目 manifest 固定该文件的提交、大小和 SHA-256，选择有依据；文件哈希不证明实物正在运行它。 |
| 控制协议 | 7-bit 地址 0x2C；VERSION resource 48 / command 0；读响应含状态，64 为重试；当前实现与官方框架一致。 |
| 物理静音 | GPO_READ_VALUES 的 X0D30，位于五字节返回的第二项；高电平表示静音。与当前实现一致。 |
| 输出设备 | 3.5 mm 接有源音箱或耳机合理。设备本身没有内置扬声器。 |
| 维护入口 | XIAO BOOT/RESET 用于 ESP32；XMOS 的 Mute+上电 Safe Mode 用于 XMOS 恢复，两者不能互代。 |

## 需要处理的问题

### P1：错误采样时钟下仍放行播放（补充 review，已用实际代码复现）

`firmware/main/runtime.c:115` 以相邻 DMA 完成间隔不超过 5 ms 认定 transport_ready，并恢复播放；250 ms 的采样率检查仅更新 capture_clock_ok。48 帧以 3 ms 周期完成时，实际速率为 16 kHz，但仍满足该播放放行条件。此时标称 48 kHz 的 USB 播放流可以进入错误速率的 I²S 总线；名义采样率附近的反馈调整不能纠正三倍时钟差异。

在 `/tmp/voicekey-review-wrong-clock.c` 中复用现有 `tests/test_runtime.c`、生产 `runtime.c` 和其原有驱动替身，补充错误时钟下打开播放并发送非零 PCM 的探针，UBSan 编译运行得到：`rate=16000 capture_ok=0 playback_active=1 output=80871424`。这是软件逻辑复现，不是实机声学结果。现有错误时钟测试仅检查 capture_clock_ok，未覆盖该播放条件。

建议将经过验证的 48 kHz 传输时钟资格用于录音与播放的共同基础条件；未合格或资格丢失时，拒收/清空播放数据并输出零。麦克风物理静音仍只影响采集，不能混入播放静音条件。增加错误速率持续输入、运行中速率改变及恢复后无旧音频的回归测试。本轮未修改实现。

### P0：USB 启动失败没有可用的应用层诊断入口（已确认）

`firmware/sdkconfig.defaults` 关闭控制台，正常诊断仅通过 HID Feature Report；USB 未枚举时无法读取这些诊断。`firmware/main/app_main.c` 在启动 USB 后立即继续 I²C、音频、模型初始化，缺少可独立运行的分阶段诊断配置。

应增加维护用最小启动配置，先独立验证启动、内存与 USB，再逐项接入控制、I²S、模型。维护镜像可以使用临时 USB 串口；不必改变正式产品“无常驻主机程序、无额外正式端点”的契约。GPIO43/44 已用于音频，不能直接恢复 UART0 日志并同时运行音频。

尚不能确认是 USB 描述符、启动崩溃、内存、调度或其他运行时问题。USB 初始化在 XMOS 初始化之前，因此“XMOS 固件不匹配”不能直接作为整机未枚举的既定根因。

### P1：实物 XMOS 固件配置尚未闭环（已确认）

当前代码严格要求版本 1.0.8、INT 配置、指定路由和格式，而实际板上版本、主从角色、采样率均未读出。出厂为 I²S 不等于出厂就是所需 48 kHz 主模式。

应先用可诊断镜像读取 VERSION、构建信息、格式与 I²S 状态，再核对时钟。若不匹配，按独立维护流程核对镜像哈希后更新 XMOS，保留 Factory 恢复入口。FAQ 中 USB v2.x 的更新不等于本项目应换用 USB 固件；那会改变所需架构。即使 VERSION 一致，也不能仅凭版本号证明镜像变体一致。

### P1：播放路由、模拟输出与 AEC 的证据不足（待实机验证）

官方 I²C 页面区分 Host→XVF3800→DAC 与 Host→DAC 两条 I²S 路径。我们的设计要求前者，但不能仅凭 `TX GPIO44`、向总线发送 PCM 或 AEC 状态可读，就认定实际参考与扬声器信号匹配。

需要记录目标镜像下的播放路径、AIC3104 模拟输出状态、输出音量，以及参考增益/旁路状态，并用已知信号验证 3.5 mm 出声和回声抑制。数字音量位于送往 XMOS 之前可以保留；还需确认 DAC 未静音且模拟增益适当。

特别澄清：官方 HA 教程引用了 AIC3104 驱动，但核对所引用仓库当前实现后，其 `setup()` 为空，主要写音量/静音寄存器。因此“项目没有 AIC3104 驱动”不是已经证实的初始化 bug，也不能直接复制该驱动来修复。控制责任和总线访问方式必须与目标 XMOS 镜像及硬件路径一起核对。

### P2：可选诊断与采集有效性耦合过强（代码行为已确认，是否调整需设计决定）

`voicekey_xvf.c` 中任一 AEC 状态读取失败会清除 configured/valid；`board.c` 中 LED 写入失败也使整个状态失效，导致采集关闭。保守关闭符合隐私取向，但会使非静音功能的错误表现为麦克风不可用。

建议区分静音新鲜度、音频格式、总线健康和可选诊断有效性，保留总线故障或静音过期时的失效关闭。不能为了可用性绕过物理静音保护，也不能在没有故障模型和测试前直接取消现有保护。

另一个限制：`board.c` 虽然在无效状态选取紫色，却只在 `next.valid` 时发送 LED 命令，所以不能保证控制故障时显示紫灯。应把故障灯标为尽力而为，并通过维护日志诊断；总线失效时软件无法保证灯色。

### 优化项：唤醒和语音输入的通道选择需要对比

HA 示例将 micro_wake_word 与 voice_assistant 分别选用不同通道索引；我们的 USB 与 WakeNet 共用左声道自动选束输出。这不是已证实错误，也不应机械交换左右声道。应在锁定路由后对 conference/ASR 处理结果做相同录音和唤醒测试，再决定是否拆分。

### P2：当前 OpenSpec 的范围说明已落后于实机阶段

`openspec/changes/migrate-respeaker-xvf3800/design.md:3` 仍写 Hardware absent，第 7 行将 hardware validation 列为 Non-goals。这可以描述先前仅软件迁移阶段，但当前已连接并首次烧录，应标注历史适用范围或更新当前范围，将实际 USB 枚举、双工播放、AEC 和恢复验证纳入后续完成条件。不能用已通过的软件测试关闭当前实机故障。

## 建议的验证顺序

1. 恢复 XIAO ROM 下载入口，保留现有完整 Flash 备份。
2. 最小诊断镜像验证 XIAO 启动、Flash/PSRAM、USB 枚举与持续运行。
3. 单独验证 I²C VERSION、静音状态和 XMOS 目标配置；必要时单独维护 XMOS。
4. 验证 48 kHz 时钟、32-bit 槽位中的有效数据、左右路由及持续双工。
5. 验证已知 PCM 经目标路径从 3.5 mm 播放，确认 DAC 音量/静音与参考路径。
6. 逐项接入 UAC 输入、输出、反馈、HID，再加入本地模型。
7. 最后测扬声器回声、双讲、误唤醒、远场及 ChatGPT 首句和打断行为。

官方网络录放音示例不能代替自定义 USB Audio + HID 的 macOS 验证；分时录放也不能代替全双工验收。此处没有证据要求推翻单 USB 产品方向，但它仍是需要我们自行完成验证的实现。
